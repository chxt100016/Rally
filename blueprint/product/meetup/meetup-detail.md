## 一句话价值

为用户交付约球详情、参与状态、费用与赛后信息。

## 核心概念

- 约球  围绕一次明确时间、场地、人数和参与条件组织的网球活动，不只是两人邀约。
- 约球发布者  创建约球并负责活动信息、费用和报名审批的人，也是首位参与者。
- 约球报名  用户与约球之间的参与关系，可处于待审批、已加入、已拒绝、已撤回、已退出、已评价或已跳过。
- 有效参与者  报名处于已加入、已评价或已跳过的人；约球发布者也属于有效参与者。
- 操作状态  结合约球实际进度、当前用户角色和报名状态得到的当前可行动阶段，不等同于约球的存储状态。
- 收款码  约球发布者提供的线下费用收取图片，不代表平台已完成收款或记账。
- 赛后复盘  约球结束后记录比分、评价同场用户或明确跳过评价的阶段。

## 状态机

无

## 主流程

触发源：用户直接或从分享场景发起 HTTP 查询；终态：交付符合当前用户视角的完整约球详情，不改变任何业务对象状态。

1. 根据约球编号取得约球及其全部约球报名，并依据当前时间判断约球实际处于报名中、进行中、已结束或已关闭。
2. 交付约球标题、类型、人数、城市、时间、场地、NTRP 要求、性别要求、加入方式和已保存状态，并补充场地背景、日出与日落。
3. 交付约球发布者的昵称、头像、性别、NTRP 和历史发布次数。
4. 按当前用户视角筛选参与者：约球发布者额外看到待审批人，其他用户只看到有效参与者；为可识别的参与者补充档案和球友等级。
5. 结合约球实际进度、当前用户是否为约球发布者、报名状态及是否已评价，交付当前操作状态。
6. 当前用户尚未报名且处于可报名操作状态时，汇总资料完善度、满员、性别、NTRP 和信誉分限制，交付是否可报名及全部限制原因。
7. 约球设有费用明细时，交付费用总额、当前用户费用角色、计算人数和分摊金额；有人时方案时同时交付分摊明细及说明，有收款码时附带其访问地址。
8. 当前用户可以进入约球群聊时，交付未读消息数；其他用户不交付未读数。
9. 约球实际处于进行中或已结束时，交付可评价球友、本人已填评价、默认标签和按盘排序的全部比分。
10. 汇总以上信息，交付当前查询时刻的约球详情。

## 分支与异常

| 什么情况 | 怎么处理 | 对外提示 | 做了一半的怎么收场 |
|---|---|---|---|
| 未登录、登录已过期或登录凭证无效 | 拒绝查询 | `未登录，请先登录`、`登录已过期，请重新登录`或`登录凭证无效，请重新登录` | 本服务只读，没有业务对象需要恢复。 |
| `meetupId` 找不到对应约球 | 终止查询 | `约球不存在` | 本服务只读，没有业务对象需要恢复。 |
| 约球已关闭 | 仍交付详情；有效参与者得到 `CLOSED_JOINED`，其他用户得到 `CLOSED` | 查询成功 | 未修改任何业务数据。 |
| 约球正在进行 | 已加入者得到 `ONGOING_JOINED`，未加入者得到 `ONGOING`；同时交付赛后复盘 | 查询成功 | 未修改任何业务数据。 |
| 约球已经结束且存在其他有效参与者 | 未加入者得到 `FINISHED`；参与者按本人是否已评价或跳过得到 `FINISHED_JOINED` 或 `FINISHED_REVIEWED` | 查询成功 | 未修改任何业务数据。 |
| 当前用户是约球发布者且没有其他有效参与者，约球未关闭 | 无论是否已进行或已结束，均交付 `OWNER_EDITABLE` | 查询成功 | 未修改任何业务数据。 |
| 当前用户的报名为 `PENDING` | 交付 `PENDING_REVIEW`；参与者清单是否包含本人取决于当前用户是否也是约球发布者 | 查询成功 | 未修改任何业务数据。 |
| 当前用户未报名，且约球允许继续报名 | 交付 `JOIN_DIRECT` 或 `APPLY_APPROVAL`，并同时交付全部报名限制 | 查询成功 | 未修改任何业务数据。 |
| 未报名用户存在一项或多项报名限制 | `joinable` 为假，并同时交付全部限制原因 | 查询成功 | 未修改任何业务数据。 |
| 非约球发布者查看参与者 | 不交付 `PENDING` 报名，只交付 `JOINED`、`REVIEWED` 和 `SKIPPED` | 查询成功 | 未修改任何业务数据。 |
| 参与者的 `user` 资料不存在 | 仍交付报名用户编号、报名编号、状态和申请时间，昵称、头像、性别与网球档案为空 | 查询成功 | 未修改任何业务数据。 |
| 约球没有费用明细 | 不交付费用视图 | 查询成功 | 未修改任何业务数据。 |
| 约球有费用明细但发布者没有收款码 | 正常交付费用，`paymentCodeUrl` 为空 | 查询成功 | 未修改任何业务数据。 |
| 约球采用人均分摊 | 报名中按人数上限均分，其他实际状态按有效参与者人数均分 | 查询成功 | 未修改任何业务数据。 |
| 约球采用人时分摊，但当前用户不在任何分摊时段 | 当前用户金额为 `0`，分摊说明为空 | 查询成功 | 未修改任何业务数据。 |
| 当前用户不可进入群聊 | 不交付 `unreadCount` | 查询成功 | 未修改任何业务数据。 |
| 当前用户可进入群聊但没有 `rally_meetup_chat_user` 记录 | 将本约球已有的全部消息计为未读 | 查询成功 | 未修改任何业务数据。 |
| 约球尚未进行 | 不交付赛后复盘 | 查询成功 | 未修改任何业务数据。 |
| 约球进行中或已结束，但没有比分或本人评价 | 交付空比分或空评价，`scoreFilled` 为假 | 查询成功 | 未修改任何业务数据。 |
| `review.default_tag` 为空 | 不交付默认标签，其余赛后复盘正常交付 | 查询成功 | 未修改任何业务数据。 |
| 七牛云无法生成头像、比分头像或收款码访问地址，或任一资料读取失败 | 终止查询 | `系统异常，请稍后重试` | 本服务只读，没有业务对象需要恢复。 |

## 业务边界

- 本服务负责向已登录用户交付一场既有约球在当前时刻的基本资料、约球发布者资料、参与者视图、当前操作状态、报名限制、费用分摊、群聊未读数和可用的赛后复盘。
- 本服务只判断并展示当前视角，不建立、修改、关闭约球，不发起、撤回或审批约球报名，也不改变任何报名状态。
- 本服务不发送或拉取群聊消息，不推进已读位置；群聊未读数只用于详情展示。
- 本服务不新增、修改或删除比分，不提交评价，也不把用户标记为已评价或已跳过。
- 本服务计算的费用仅用于线下分摊展示，收款码不代表平台收款，不创建支付单、不核实付款结果，也不记录谁已付款。
- 本服务不限制普通已登录用户查看约球、有效参与者、费用及可用赛后复盘；待审批名单仅约球发布者可见。
- 本服务交付到详情或明确查询失败为止，不负责详情之后的报名、群聊、编辑、支付或赛后复盘动作。

## 遗留与待定

- `shareUserId` 当前只被接收但不参与分享人展示、归因、邀请关系或访问权限判断；该字段的业务目的和是否保留应由产品确认。
- `rally_meetup.status` 按存储值交付，但操作状态按当前时间重新判断；定时结算前可能出现 `status=OPEN` 而 `actionState` 已是进行中或已结束，前端以哪个为准应由产品确认。
- 部分既有查询仍把 `FULL` 或 `full` 当作约球状态，但详情只识别 `DRAFT`、`OPEN`、`ONGOING`、`CLOSED`、`FINISHED`；历史数据是否存在该值以及统一迁移口径应由产品与数据负责人确认。
- 约球发布者没有其他有效参与者时，即使约球已进行或已结束也会得到 `OWNER_EDITABLE`；实际编辑规则又不允许终态约球编辑，两处承诺冲突，应由产品确认展示状态并由研发统一。
- `DRAFT` 没有独立的详情操作状态；知道草稿编号的未报名用户会得到 `JOIN_DIRECT` 或 `APPLY_APPROVAL`，草稿的可见范围和可操作性应由赛事与产品负责人确认。
- 约球实际处于进行中时已开始交付赛后复盘，且进行中或已结束的复盘对所有已登录用户可见；比分、评价目标和复盘入口的可见范围应由产品确认。
- 详情不按 `review.deadline_days` 截止复盘展示，已过评价期限的参与者仍可能得到 `FINISHED_JOINED`；是否应隐藏评价入口或交付“已过期”状态应由产品确认。
- `scoreFilled` 当前表示本场是否存在任意比分，而字段注释称“当前用户是否已填比分”；其正式业务含义应由产品确认。
- 费用视图会向 `COLLECTOR`、`PAYER` 和 `STRANGER` 三种角色都附带约球发布者收款码，与“仅收款人视角返回”的字段说明冲突；收款码可见范围应由产品和隐私负责人确认。
- 报名中费用固定按 `max_players` 计算，进行中、已结束或已关闭则按有效参与者数计算；这可能与交付的 `current_players` 不一致，费用人数的唯一口径应由产品确认。
- 人时分摊先按活动总时长折算小时费用，分段除以人数后保留两位，再以整数分截断；各人金额之和可能与总金额不一致，尾差归属规则应由产品和财务负责人确定。
- 场地背景当前没有真实天气资料，室外一律按晴天；找不到球场材质或室内外环境时按室外硬地处理，降级规则是否符合展示承诺应由产品确认。
- 日出与日落固定按上海时区（UTC+8）计算，不随活动城市变化；跨时区城市的业务口径应由产品确认。
- 用户性别字段为 `null` 时会被视为符合性别限制，而 `UNDISCLOSED` 会得到 `GENDER_UNKNOWN` 限制；两种“未知性别”的准入口径应由产品统一。
- 参与者缺少 `user` 资料时仍会出现在清单中，但约球发布者资料缺失可能导致整个查询失败；异常数据的展示和修复责任应由产品与数据负责人确定。
- 球友等级使用信誉分、可信度、校准度及平台配置计算，但这些分值为空时的展示规则没有业务定义；应由产品和评分负责人确认。
