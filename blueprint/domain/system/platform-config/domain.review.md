## 已确认

- [Q1] 配置聚合边界是一条 key+scope 记录还是全部平台配置，缓存是否在事务边界内？
  > 每个 configKey+scope 是独立聚合；JVM/分布式缓存是事务外投影，只能在数据库提交后失效或重建。
  → 边界与缓存边界情况

- [Q2] 配置值长度采用应用当前 100000 字符还是数据库 2048 字符上限？
  > 领域契约采用持久化真实上限 2048 字符；结构化 JSON 紧凑序列化后仍超过上限则拒绝，不把数据库异常当参数校验。
  → I3、C1 与长度边界情况

- [Q3] 版本、valueType 与 enabled 在首次发布和更新时如何变化？
  > 首次提交 expectedVersion=0，建立 version=1；更新必须精确匹配并原子加一。valueType 由配置名录定义且不可漂移，发布会置 enabled=true；停用用独立版本化命令。
  → 状态、I2/I4、C1/C2

- [Q4] 配置发布是否应保留 main 的100000字符应用上限与事务内当前JVM全量缓存重建，而不是按2048提前拒绝并afterCommit广播？
  > 保留 main：应用只拒绝超过100000字符；2049至100000进入DB并可能系统失败。写库后同事务内调用SystemConfig.init全量重建当前JVM，回滚不补偿且不广播其他实例。
  → 已修正边界、I3、C1、边界情况和实现提示，记录真实长度与缓存时序。

- [Q5] 完整首页 JSON 是否继续由 @system.platform-config 聚合的 C1 发布命令承载，而不拆分新的首页配置聚合？
  > 是，完整首页 JSON 继续使用 @system.platform-config 的 C1 发布命令，不新建首页配置聚合。
  → 落实到命令 C1 后的首页配置说明。

- [Q6] 首页配置在聚合中的身份是否唯一收敛为 home.page.config，旧三项 key 仅保留历史数据库记录且新发布按未知 key 拒绝？
  > 是，正式首页配置身份唯一为 home.page.config；旧三项 key 的历史记录保留但退出名录，新发布按未知 key 拒绝。
  → 落实到不变量 I2、命令 C1 与首页配置边界说明。

- [Q7] 本次首页配置合并是否改变 sys_config 表归属、乐观版本规则或 JVM 缓存刷新边界？
  > 不改变；sys_config 仍由该聚合持有，首次版本、乐观锁加一与当前 JVM 缓存刷新边界保持原样。
  → 落实到边界、I4、C1 和边界情况，确认无需迁移。
