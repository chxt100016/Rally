## 已确认

- [Q1] currentPlayers、容量与同一用户重复报名应采用什么聚合内口径？
  > currentPlayers 等于 JOINED/REVIEWED/SKIPPED 状态下去重 userId 数量，创建者只有持有有效报名才计入；不得超过 maxPlayers。同一用户最多一条 PENDING 或有效报名，根行加锁串行保护，无需新增表约束。
  → I2、I3、C4/C5 与并发及创建者人数边界情况

- [Q2] OPEN/FULL/ONGOING/FINISHED 的状态由存储值还是时间与人数推导，大小写如何统一？
  > 领域状态统一大写语义、持久化统一小写；DRAFT/CLOSED/FINISHED 为显式状态，其他活跃状态按当前人数和 start/end 时间推导。到 startTime 即 ONGOING，到 endTime 即 FINISHED 候选。
  → 约球状态、I6 与时间边界情况

- [Q3] PENDING 报名是否获得聊天、比分和评价参与资格，发布者是否可以退出自己的普通约球？
  > PENDING 只表示待审批，不获得参与资格；只有创建者身份本身或 JOINED/REVIEWED/SKIPPED 才可聊天，只有有效报名参与者可比分和评价。普通约球发布者不能退出自己的报名，应关闭约球。
  → 报名状态、资格查询、C8 与待审/发布者边界情况

- [Q4] 赛事约球的编辑、开放和关闭由本聚合独立决定，还是接受比赛聚合的外部结论？
  > 约球聚合不读取比赛；调用方把比赛仍允许编辑、全员确认或需要终止的结论作为命令输入。赛事约球只有外部结论明确允许时才能编辑、DRAFT 转 OPEN 或 DRAFT 转 CLOSED。
  → 外部引用、边界、C2/C3/C11/C12 与赛事边界情况

- [Q5] 报名审批、拒绝、撤回、退出与复盘状态迁移是否必须带原状态条件？
  > 必须。所有报名迁移在聚合锁内校验精确前置状态，持久化使用原状态条件并检查影响行数；并发变化返回冲突，不允许后写覆盖已提交终态。
  → I7、C5-C9 与实现提示中的条件更新

- [Q6] 约球编辑契约是否按现实现状记录：只走接口字段校验和编辑锁，不复用发布时的 duration/NTRP 组合校验，并允许 maxPlayers 低于现有人数？
  > 是。领域契约必须忠实记录现有编辑路径：接口字段校验与编辑锁继续生效，但不复用发布级 duration/NTRP 组合校验，也不阻止 maxPlayers 低于当前人数。
  → 已落实到不变量 I4/I5、命令 C3 与边界情况。

- [Q7] 普通约球关闭与退出是否保留现有宽松边界：无其他参与者时 FINISHED 也能关闭，发布者本人可退出，退出不检查约球状态或开始时间？
  > 是。无其他有效参与者时 FINISHED 普通约球仍可关闭；创建者可退出自己的普通约球，退出不检查根状态或开始时间。
  → 已落实到状态表、命令 C8/C10、边界情况与实现提示。

- [Q8] 并发保障是否只描述当前无版本号、无显式根行锁、按 bizId upsert 和最后写入生效，而不声称已有数据库级唯一或乐观锁保证？
  > 是。只描述当前按 bizId upsert、无版本列、无显式根行锁或活动报名唯一约束的事实，并明确并发最后写入与超员风险。
  → 已落实到不变量 I3/I7、并发边界情况与实现提示。

- [Q9] PENDING 报名者是否具备聊天资格，还是必须等批准为 JOINED 后才能进入聊天？
  > 保留 main 行为：PENDING 属于 findActiveRegistration，可聊天但不占参与名额；比分和评价资格仍按各自规则判断。
  → 命令章节后的资格说明已加入 PENDING，并区分聊天资格与参与名额。

- [Q10] C14 是否应限制终止状态并校验费用项金额，还是保留 main 在任一状态原样保存费用项、只校验非空分摊方案的行为？
  > 保留 main 行为：任一状态均可替换；费用项原样保存；只校验非空分摊的总时长、正时长和参与资格，空 duration 自然产生系统异常。
  → I8、C14 与边界情况已对齐 editPrice 现有行为和异常分档。

- [Q11] PENDING 报名是否只可聊天，还是按 main 的 assertIn 同样可在阶段和期限允许时提交比分与评价？
  > 保留 main：PENDING 通过 assertIn，可聊天，并可在 ONGOING/FINISHED 且未过期限时提交比分或评价，但仍不占参与名额。
  → 资格说明与待审边界已对齐 assertIn/assertReviewAvailable。

- [Q12] 批准 PENDING 报名是否应在满员时拒绝，还是保留 main 不检查容量并允许审批后超员？
  > 保留 main：C5 不检查容量或 expiresAt，PENDING 转 JOINED 后重算人数，达到或超过上限仍成功。
  → I2、C5 与待审边界已改为审批不检查容量且允许超员。

- [Q13] 跳过评价是否与提交评价共用参与资格和截止期校验，还是保留 main 只校验 ONGOING/FINISHED、JOINED 零行也成功？
  > 保留 main：跳过仅校验实际状态 ONGOING/FINISHED，不校验参与资格或截止期；批量更新本人 JOINED，零行也成功。
  → C9 拆为完成评价，新增 C15 跳过评价，并补充零行/超期边界。
