## 已确认

- [Q1] 聚合边界是单条评价维度，还是一位评价人在一场约球中的完整评价集合？
  > 以 meetupId+fromUserId 的完整评价集合为聚合边界，每个目标用户的一个评价维度是内部实体；一批提交在同一事务中校验和保存。
  → 聚合根、实体与边界

- [Q2] 是否允许评价自己或非本场有效参与者，目标资格由谁提供？
  > 不允许自评或评价非本场有效参与者。约球聚合先给出有效参与者集合，评价聚合只接受该外部结论作为命令输入，不自行读取报名表。
  → 外部引用、I2 与目标边界情况

- [Q3] 同一目标达到评价覆盖需要任意一个维度，还是所有固定维度？
  > 保持当前产品口径：目标用户存在至少一个合法维度评价即算已覆盖；完成全部评价需覆盖除本人外所有有效参与者，不要求三个维度齐全。
  → 命令后的覆盖查询说明与覆盖边界情况

- [Q4] 一次请求内重复提交同一目标和维度时按顺序后项覆盖，还是拒绝歧义？
  > 拒绝重复键，避免列表顺序决定最终值；跨请求再次提交同一维度则覆盖 reviewValue 并沿用原 bizId。
  → I1、I4、C1 与批次重复边界情况

- [Q5] 评价目标是否必须是非本人同场参与者，还是保留 main 不校验目标资格的行为？
  > 保留 main：不校验目标账户、同场资格或自评，只把请求 toUserId 用于唯一维度。
  → 边界、I2、C1 与边界情况已移除目标资格强校验。

- [Q6] 同一请求重复目标维度应拒绝，还是按 main 列表顺序由后项覆盖前项并允许空列表？
  > 保留 main：逐项 upsert，批内重复维度后项覆盖前项；空列表成功并允许下游覆盖检查。
  → I4、C1、边界情况与实现提示已改为顺序覆盖和空列表成功。

- [Q7] TAG 是否去空白后非空且限制 512 字符，还是保留 main 只拒绝 null？
  > 保留 main：TAG 只拒绝 null，允许空白、自定义和逗号串，不增加 trim 或 512 长度校验。
  → I3 与实现提示已按现有值校验对齐。
