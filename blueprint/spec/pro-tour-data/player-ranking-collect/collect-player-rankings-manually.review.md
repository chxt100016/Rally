## 已确认

- [Q1] HTTP 入口的鉴权、参数与成功响应精确是什么？
  > GET /tour/collect/rank 位于 WebMvcConfig 普通 AuthInterceptor 排除清单，不校验登录或运营身份，不接收入参。完整执行或一个/两个来源为空被跳过时均返回原始字符串“排名采集完成”；未处理异常走全局失败响应。
  → 已写入触发、接口契约、详细流程第 1/7 步及鉴权技术线索

- [Q2] ATP/WTA 来源为空与来源抛出异常分别如何继续或终止？
  > ATP 先于 WTA。任一来源 response/data/rankings/players 为空时该巡回赛只记警告并跳过，流程继续；客户端调用或后续未捕获异常会向上抛出。ATP 抛错会阻止 WTA，WTA 抛错则在 ATP 已处理后终止。
  → 已写入详细流程第 2/6 步、流程图与来源为空/异常分支

- [Q3] 球员身份、本批去重、非空覆盖以及来源遗漏记录的规则是什么？
  > 以 tour+playerId 严格识别；保存前过滤两者任一为空的记录，并用 LinkedHashMap 在批内去重，同键后到记录只以非空字段合并。存量同键记录也仅由非空字段覆盖；本次来源未出现的存量球员保持原状。
  → 已写入详细流程第 3-4 步、异常补充说明与服务边界

- [Q4] ATP 与 WTA 的事务边界及部分成功结果是什么？
  > ATP 与 WTA 分别调用带事务的 saveOrUpdateBatch，各自独立提交。单批异常回滚该批；ATP 成功提交后 WTA 失败不会回滚 ATP。流程没有跨巡回赛原子性或补偿。
  → 已写入详细流程第 5-6 步及 ATP/WTA 独立回滚分支

- [Q5] 出生日期和缺少必填资料如何处理，是否返回统计？
  > 出生日期仅取来源字符串前十位按 ISO 日期解析，空白、过短或非法都转为 null，因此存量不刷新、新球员可为空。姓名等其他来源字段也不校验，存量保留旧值；新记录触发数据库必填约束时整批失败。接口不返回任何计数或分巡回赛结果。
  → 已写入成功响应、详细流程第 3/7 步及异常补充说明
