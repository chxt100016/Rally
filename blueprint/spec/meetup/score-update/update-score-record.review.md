## 已确认

- [Q1] 提交的 version 是否真正进入更新条件并在成功后递增，两个并发修改如何裁决？
  > 不真正乐观锁。服务只在更新前读取现值并与提交 version 比较；重建的 ScoreRecordData 没有携带 version，转换后的更新实体 version 为 null，插件因而不追加版本条件也不递增。两个请求可同时通过比较并按写入顺序覆盖，更新行数未检查。
  → 已在触发、契约、详细流程、异常说明、技术线索和服务边界明确版本仅内存比较，更新无版本条件与递增，并发可覆盖。

- [Q2] 把可选球员、抢七分设为空，或换成无档案球员时旧字段能否被清除？
  > 通常不能。仓储以实体更新且采用默认非空字段策略，null 字段不会进入 SET；因此 player2、tiebreakScore 设 null 会保留旧值。新球员查不到档案时新快照为 null，已有昵称、头像和性别也可能残留并与新 userId 不一致。
  → 已在契约、详细流程、异常说明和技术线索明确默认非空更新导致旧可选字段和资料快照可能残留。

- [Q3] 修改盘号时是否预检同场唯一，冲突如何对外表现？
  > 不预检。服务只按 bizId 读取原记录，不查询新 setNum 是否被其他记录占用；若改变后与同约球其他盘冲突，数据库 uk_meetup_set 唯一键拒绝，落入系统异常，原记录保持不变。
  → 已在契约、详细流程、异常分支和技术线索明确修改前不查重，由数据库唯一键以系统异常拒绝冲突。

- [Q4] 谁可以修改比分，是否要求原记录人或本盘球员？
  > 发布者，或首条活动报名为 PENDING、JOINED、REVIEWED、SKIPPED 的用户均可修改。权限属于约球层面，不检查 recordedBy，也不要求修改人出现在任何球员位置；成功后 recordedBy 会改为当前修改人。
  → 已在详细流程、异常分支和服务边界明确约球级权限，不要求原记录人或阵容成员，记录人改为修改人。

- [Q5] 修改后的阵容与计分采用哪些业务校验，成功后返回什么？
  > 除必填与枚举转换外，只校验两侧主分不相等并以较大者为胜方；不校验盘号范围、阵容人数和资格、重复占位、分数范围、盘制计分或抢七组合。成功只返回通用成功标识，不返回新版本或比分内容。
  → 已在契约、详细流程、异常说明和服务边界明确仅校验主分不等，不做阵容与计分规则校验，成功无业务数据。
