## 已确认

- [Q1] 邀请是否校验被邀请人身份、档案和普通报名准入，以及约球状态、时间和类型？
  > 按 Java 实现确认：只校验当前用户是发布者、当前有效人数未满、被邀请人无 PENDING 或有效报名。不会查询被邀请人账户与档案，也不做性别、NTRP、信誉、时间冲突校验；不检查约球 status、start/end、joinMode 或 meetupType。
  → 已落入详细流程、请求参数和服务边界。

- [Q2] 名额和重复报名在并发邀请下如何保证，哪些历史报名允许再次邀请？
  > 按 Java 实现确认：isFull 和 findActiveRegistration 都基于已加载聚合，没有乐观锁、名额占用或用户约球唯一约束。REJECTED、WITHDRAWN、QUIT 不算活动报名，可新插一条 JOINED；并发可能超员或产生重复活动报名。
  → 已落入触发、详细流程和异常分支后的并发说明。

- [Q3] 报名保存后群聊成员已存在或建立失败时，报名和当前人数如何收场？
  > 按 Java 实现确认：invite 应用方法有事务，先整体保存约球与报名并重算 currentPlayers，再 chatDomainService.join。群聊已存在报 ALREADY_JOINED_CHAT，或群聊保存失败时同一事务回滚报名与人数；通知只注册为提交后异步执行。
  → 已落入成功响应、流程图和异常分支。

- [Q4] 邀请建立的报名业务编号以及邀请成功通知，Java 实际如何处理？
  > 按 Java 实现确认：新 RegistrationData 未设置 bizId，映射与保存路径也不补业务编号，仅数据库 id 自增；接口不返回报名编号。未满员不发送任何邀请成功通知；只有本次后 isFull 为真才向全部有效参与者尝试 TEAM_SUCCESS，且没有已通知去重标记。
  → 已落入详细流程、成功响应和异常分支后的通知说明。

- [Q5] 补充检查 RegistrationData 构造器后，新邀请报名是否实际生成业务报名编号？
  > 更正先前 Q4 的部分结论：RegistrationData 无参构造器会通过 IdWorker 立即生成 bizId，因此邀请创建的新报名具有业务报名编号，聚合保存按该编号插入；只有接口不返回该编号的结论不变。
  → 已更正详细流程、异常说明和服务边界；保留接口不返回报名编号。

- [Q6] 邀请是否继续直接形成 JOINED，且不校验账户、档案与普通报名准入？
  > 是。按原业务由发布者直接邀请为 JOINED，不新增账户、档案、性别、NTRP、信誉或时间冲突校验。
  → 已落入详细流程第 3 至 5 步与服务边界。

- [Q7] 邀请后达到人数上限时是否向当时全部有效参与者发起组团成功通知？
  > 是。邀请后达到或超过人数上限时，事务提交后向当时全部有效参与者发起组团成功通知。
  → 已落入业务活动、流程图与详细流程第 7 步。

- [Q8] 组团成功通知失败是否不回滚报名、人数与群聊关系？
  > 不回滚。通知不可达、已退出、缺少身份或发送失败只跳过或记录失败。
  → 已落入详细流程第 8 步与异常分支说明。
