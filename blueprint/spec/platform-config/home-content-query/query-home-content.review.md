- [Q19] 海报可见城市控制应放在哪一层，城市不匹配时如何交付？
  > cityId 只放在 POSTER 区块；缺失、null 或空白表示全城市，非空与最终 cityCode 原字符串精确匹配。不匹配时省略整个区块，单张海报上的旧 cityId 不再产生可见性效果。
  → 已落实到详细流程第 5 至 6 步、区块城市筛选异常分支和技术线索。

## 已确认

- [Q1] 匿名/无效令牌和城市参数如何处理，首页布局解析失败怎样降级？
  > 接口 OptionalAuth；缺失/无效令牌均匿名继续。cityCode 为 null 或 trim 后空用 330100，否则保留原字符串且不校验。布局解析抛异常回退枚举默认 JSON；若解析结果为 null 等导致遍历前异常，则无法局部降级，整个请求按系统异常失败。
  → 接口契约、详细流程第 1-2 步与默认配置/SYSTEM_ERROR 分支

- [Q2] 区域启停、未知类型与单区域构建失败如何影响整体顺序和结果？
  > 仅 enabled 明确为 false 才跳过；空 section、空/未知 type 跳过。buildDisplayItem 内任何异常由每区域 try/catch 吞掉并省略该区域，后续区域继续，成功项保持配置顺序；但 getJSONObject 发生在 try 外，其异常可终止整体。
  → 详细流程第 2-3、14 步与区域省略分支

- [Q3] 我的约球区域对匿名和登录用户的筛选、排序、数量与分页口径是什么？
  > 匿名返回 MEETUP 区域但 meetups=[]。登录时筛 JOINED/REVIEWED/SKIPPED、约球 OPEN、end_time>NOW，biz_id DESC，内部多取1条判断 hasMore 后最终最多10张卡；首页只取 list，不暴露 hasMore/nextCursor。
  → 接口契约、详细流程第 4 步与业务活动

- [Q4] 三类海报区域如何取文案、签名图片和附加城市参数，坏海报如何收场？
  > 赛事海报用独立配置且不带城市；球场海报用通用海报配置并始终解析城市名；自定义海报仅 cityAware=true 带城市。图片签名1小时。城市参数直接以 ?cityCode&cityName&mode=view 拼接且不编码。列表首个无效 type、空对象、签名或城市解析异常会终止余项但保留之前海报；区域通常仍返回。
  → 详细流程第 5-9 步与部分海报异常分支

- [Q5] 职业赛事的日期、级别、合并、排序和代表赛事规则是什么？
  > 查 startDate<=明天且 endDate>=昨天；可解析整数 category<250 过滤，空/非整数保留。日期重叠且城市 trim 后忽略大小写相同即用并查集合并，允许跨 tour 与传递合并。按 GS/1000/500/250/其他、规范化 category、起止日、tournamentId 排序，组首为代表。
  → 详细流程第 10 步与技术线索

- [Q6] 每个赛事组展示哪些比赛，翻译缺失时是否会产生持久化副作用？
  > 取未完成且 matchDate 非空的比赛，再补同日期 FINISHED；双方球员均空过滤。按最早日期取排序首个球场的全部比赛。已有 zh-CN 非空缓存译文替换；缓存 miss 会逐条尝试新增 translated_text 为空的 translation 记录，失败仅记日志，原文继续。赛事组常规缺资料返回 null 跳过，但构造抛异常会省略整个 TOUR_MATCH 区域。
  → 详细流程第 11-12、14 步与翻译/赛事异常分支

- [Q7] 哪些失败会省略局部区域，哪些情况会让整个首页请求失败？资讯区域实际交付什么？
  > 首页海报/约球/职业赛/翻译/Qiniu 等区域构建异常都被区域级捕获并省略；海报项异常由列表级捕获形成部分列表。顶层布局得到 null、section 提取在区域 try 外异常、默认布局也无法解析或框架级异常会导致整个请求 SYSTEM_ERROR。NEWS 总是返回区域文案和空 newsItems。
  → 详细流程第 3、13-14 步与完整异常分支

- [Q8] 完整首页 JSON 缺失、根结构错误或 sections 无法遍历时如何处理？
  > 读取 home.page.config；当前值缺失时由系统配置机制提供完整默认 JSON，解析失败、根对象错误或 sections 不是数组时均整体回退完整默认 JSON。默认 JSON 仍无法使用才终止首页请求。
  → 已落实到详细流程第 2 步和默认配置异常分支：完整配置结构异常时整体回退默认 JSON。

- [Q9] 海报城市过滤与图片签名、交互解析和城市感知导航的先后顺序是什么？
  > 先按 cityId 过滤海报；不匹配的海报不做交互解析、图片签名或导航处理。匹配后再按配置顺序转换，cityAware 区域最后为非空导航目标附加本次城市信息。
  → 已落实到详细流程第 5 至 7 步：先按 cityId 过滤，再解析、签名并处理 cityAware 导航。

- [Q10] 一个海报区域经城市过滤后没有任何可见海报时是否仍交付区域？
  > 仍交付该 POSTER 区域的标题、副标题和空 posters 数组，不因城市筛选为空而省略区域。
  → 已落实到详细流程第 6 步：筛选为空仍交付标题、副标题和空 posters。

- [Q11] 首页内容查询是否兼容旧三项配置和旧海报区域类型？
  > 不兼容。只读取 home.page.config，只识别 MEETUP、TOUR_MATCH、POSTER、NEWS；旧三项 key 和 TOURNAMENT_POSTER、COURT_POSTER 不再参与首页查询。
  → 已落实到详细流程第 2、3 步与技术线索：只读 home.page.config，只识别四种区域类型。

- [Q12] {{cityId}} 是否以本次最终 cityCode 原字符串替换，三个 URL 中出现多次时全部替换，且不查询城市名录？
  > 是，{{cityId}} 使用本次默认处理后的 cityCode 原字符串，在 wechatUrl、appUrl、webUrl 中全部替换，不查询城市名录。
  → 落实到海报处理步骤和技术线索中的 cityId 替换规则。

- [Q13] 只有任一跳转 URL 包含 {{cityName}} 时是否才查询城市名；城市不存在时只省略当前海报并继续后续海报？
  > 是；仅 URL 实际含 {{cityName}} 时查询城市名，无法取得时只省略当前海报，继续后续海报。
  → 落实到海报处理步骤和单张海报省略异常。

- [Q14] 运行时遇到未登记或残缺占位符时，是否按当前“可见海报转换失败”规则保留此前海报并停止本区域后续海报？
  > 是；未登记、空白、未闭合或无配对占位符均视为当前可见海报转换失败，保留此前结果并停止本区域后续海报。
  → 落实到海报转换步骤和部分海报异常。

- [Q15] 旧 cityAware 是否在首页查询中完全忽略，不再触发自动追加 cityCode、cityName 或 mode 参数？
  > 是；cityAware 完全忽略，不再自动追加任何参数，mode 等固定参数必须直接写在 URL 模板中。
  → 落实到海报处理步骤、服务边界和技术线索。

- [Q16] 首页查询是否将 {{cityCode}} 全部替换为本次最终 cityCode 原字符串，替换行为与原 {{cityId}} 完全一致？
  > 是，{{cityCode}} 全部替换为最终 cityCode 原字符串，不查询城市名录；仅替代原占位符命名。
  → 落实到海报处理步骤和技术线索。

- [Q17] 运行时若数据库仍保存旧 {{cityId}}，是否按未登记占位符处理并触发当前 POSTER 区域部分失败，而不是兼容替换？
  > 是，旧 {{cityId}} 不兼容，运行时按未登记占位符触发部分海报失败；运营配置需同步迁移。
  → 落实到部分海报异常和兼容边界。

- [Q18] {{cityName}}、poster.cityId 城市筛选、城市名不可用时跳过当前海报等行为是否全部保持不变？
  > 是，{{cityName}}、poster.cityId 可见性筛选及城市名不可用时的单张海报省略规则均不变。
  → 落实到详细流程和异常分支。
