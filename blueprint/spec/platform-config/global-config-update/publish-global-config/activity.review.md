## 已确认

- [Q1] 不同配置内容如何校验和规范化？
  > 首页三类 JSON 按结构/数量/类型/必填文本校验并紧凑化；其他值按默认值形式推断 long 或 BigDecimal，普通字符串不规范化；上限100000字符。
  → 已写入业务动作 A1、详细流程第 1-2 步与边界情况

- [Q2] 首次发布和已有记录的版本语义是什么？
  > 无记录只接受version=0并建version=1；已有记录以id+提交version条件更新并加一、重新启用，未命中报冲突，既有 valueType 不改。
  → 已写入业务动作 A2、详细流程第 3-4 步

- [Q3] 缓存刷新与数据库事务是否原子、是否跨实例？
  > 不原子也不跨实例；同事务内重建当前JVM缓存，后续失败数据库回滚但缓存不补偿，其他实例不通知。
  → 已写入业务动作 A3、详细流程第 5-6 步与实现提示

- [Q4] home.page.config 中 enabled、cityAware、标题和海报字段的必填与类型规则是什么？
  > sections 必须是数组；每个区域 id 和 type 必填字符串，enabled 可选且必须为布尔值、缺省为 true。POSTER 的 title 必须为非空字符串，subtitle 可选字符串，cityAware 可选且必须为布尔值、缺省为 false，posters 必须是数组。每张海报 actionType 和 image 必须为非空字符串，title、subtitle、三端 URL 与 cityId 可选但出现时必须是字符串；cityId 可为空白。
  → 已落实到活动契约、详细流程第 2 至 3 步和边界情况。

- [Q5] home.page.config 出现未识别的根、区域或海报字段时如何处理？
  > 根对象、区域和海报中的未识别字段允许存在并在紧凑序列化时原样保留，首页查询忽略它们；已识别字段仍严格校验。
  → 已落实到详细流程第 4 步和边界情况：未知字段保留，已知字段严格校验。

- [Q6] 旧三项首页 key 对应的 sys_config 历史记录如何处理？
  > 不删除也不迁移旧 sys_config 记录；旧 key 退出 SystemConfigKey 名录后不再由运营视图返回，首页也不再读取。历史记录留库但不产生运行时效果。
  → 已落实到详细流程第 1、7 步：旧 key 退出名录，历史记录留库且不再消费。

- [Q7] 发布活动是否只校验三端 URL 中的占位符，标题、副标题和其他未知字段中的 {{...}} 按普通文本保留？
  > 是，只扫描 wechatUrl、appUrl、webUrl；其他字段中的大括号文本不属于海报导航占位符校验。
  → 落实到 A1 的 POSTER 字段和占位符校验范围。

- [Q8] 通过校验的 {{cityId}}、{{cityName}} 是否原样存入紧凑 JSON，不在发布时替换或查询城市？
  > 是，两个已登记占位符原样保存；发布活动不替换、不查询城市，替换发生在首页查询。
  → 落实到 A1 规范化与详细流程。

- [Q9] cityAware 是否从已识别 POSTER 字段中移除，但因未知字段保留规则而允许随 JSON 原样保存？
  > 是，cityAware 不再作为已识别字段校验，但按未知字段保留规则原样保存。
  → 落实到 A1 的字段规则和边界情况。
