## 已确认

- [Q1] 已有收款码再次保存时是新增还是覆盖，业务编号和创建时间是否保持？
  > 按 userId+extKey 查到后更新同一数据库 id，不新增第二行；但每次 data.bizId 都为空，仓储会为 PO 新生成 bizId，所以覆盖时业务编号也变化。createTime 因新实体为 null 且非空更新策略而保留，updateTime 由数据库刷新。
  → 已在详细流程、契约和技术线索明确覆盖同一自增主键，但 extValue 与 bizId 均替换、创建时间保留。

- [Q2] 覆盖保存后旧七牛图片是否删除或进入清理任务？
  > 不删除，也没有清理任务、延迟回收或引用计数。保存服务完全不调用七牛；旧 key 被覆盖后，对应外部图片可能成为孤儿，需另行治理。
  → 已在详细流程、异常说明和服务边界明确保存服务不调用七牛且无旧资源清理。

- [Q3] 保存前是否校验账户档案、key 格式、资源存在、图片归属与内容？
  > 只用 @NotBlank 与领域 Assert.notBlank 校验 key。既不确认 user/profile 存在，也不判断 key 是七牛 key、URL 或 base64，不请求七牛验证存在性、归属、文件类型、大小或内容。
  → 已在契约、详细流程、异常说明和服务边界明确只校验非空白，不校验账户与资源。

- [Q4] 并发首次保存与并发覆盖分别如何决定成功和最终值？
  > 首次并发都可能先查不到，数据库 uk_user_ext_key 只让一条插入成功，另一条系统异常。已有行并发覆盖都按同一 id 无版本更新，最后写入者决定 extValue 与新 bizId，旧图片均不处理。
  → 已在详细流程、异常分支和技术线索明确首次并发依赖唯一键、覆盖并发最后写入者生效。
