- [Q1] 新单场取消能力是否使用独立后台接口，保留现有按赛事批量取消接口不变？
  > 是。新增独立后台接口，现有按赛事批量取消未订场比赛的接口和流程保持不变。
  → 落入触发、接口契约和技术线索：新增独立后台 POST 接口，旧批量接口不变。

- [Q2] 取消成功是否继续返回无数据响应，不额外交付被取消比赛快照？
  > 是。成功返回无数据响应，不返回比赛快照。
  → 落入接口契约：成功响应无业务数据。

- [Q3] 并发期间比赛变为另一未完成状态时，是继续取消还是要求刷新重试？
  > 若最新状态仍不是 COMPLETED，则基于最新比赛和参与关系继续取消；若已完成或已被删除，则拒绝并提示刷新。
  → 落入详细流程与异常分支：非完成状态变化重载后继续，完成或删除时失败。

- [Q4] 目标比赛已经是 REJECTED 时，重复终止是否按幂等成功处理并继续安全重试赛约与报名联动？
  > 是。REJECTED 视为已终止，重复请求幂等成功，不重复递增比赛版本；赛约关闭和报名释放按当前状态安全重试。
  → 落入触发、详细流程和异常分支的重复请求语义。

- [Q5] 运营终止复用 REJECTED 时，是否保留原拒绝、订场、确认、重订和赛果草稿字段且不新增终止审计字段？
  > 是。保留比赛根、参与者及原拒绝、订场、确认、重订和赛果草稿字段，不填写 completedTime，本次不新增终止原因、操作人或时间字段。
  → 落入接口流程、数据保留边界和技术线索。

- [Q6] 现有按赛事批量取消未订场比赛的接口是否保持原物理删除语义，仅修改指定单场接口？
  > 是。只修改 POST /tournament/admin/match/cancel/single；现有按赛事批量取消未订场比赛接口保持原物理删除语义。
  → 落入触发和技术线索的兼容边界。
