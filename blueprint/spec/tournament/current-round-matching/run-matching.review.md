## 已确认

- [Q1] 空请求、仅 tournamentId、仅 excludedEntryNos 和 manualGroups 非空时分别选择哪种匹配模式？
  > 空请求、空对象或未提供 tournamentId/manualGroups/excludedEntryNos 时走全量扫描。提供 tournamentId 且 manualGroups 为空时对指定赛事自动匹配，可同时临时排除编号。manualGroups 非空时走指定赛事手工分组后自动补配，必须同时有 tournamentId。仅有 excludedEntryNos 而没有 tournamentId 会进入指定赛事分支并因参数错误失败。
  → 已写入接口契约、详细流程第 1-2 步与参数异常

- [Q2] 手工分组与自动匹配分别应用哪些约束，手工分组落地后剩余队伍如何处理？
  > 手工组必须人数等于本轮组大小，编号非空、不重复，且都属于未排除、当前轮次 WAITING 的完整参赛队；它绕过地区、时间、性别和历史对阵约束。手工组先事务性落地，剩余 WAITING 队伍再按共同时间、地区、已完成历史对阵与方案优先级自动匹配。
  → 已写入详细流程第 3-5 步、分组异常与流程图

- [Q3] 指定赛事与全量扫描的失败边界有何不同，能否交付部分赛事结果？
  > 指定赛事的手工和自动匹配均以该赛事为事务边界，读取、校验或保存失败会整体回滚并向接口报错。全量模式逐赛事调用独立事务并捕获异常，所以失败赛事回滚、此前及后续成功赛事保留，HTTP 最终仍返回成功且不返回部分失败明细。
  → 已写入详细流程第 7 步、异常分支与技术线索

- [Q4] 新比赛如何确定 MATCHED 或 BOOKING，匹配通知失败是否影响比赛与报名终态？
  > 每组恰有一名可订场成员时直接指定该成员并创建为 BOOKING，否则创建为 MATCHED；全部组员报名改为 IN_MATCH。匹配通知按每场比赛及接收人异步尝试，未订阅或发送失败不回滚比赛和报名，也不改变接口成功。
  → 已写入详细流程第 6-7 步、通知异常与技术线索
