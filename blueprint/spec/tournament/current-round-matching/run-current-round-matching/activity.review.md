## 已确认

- [Q1] 三种执行模式如何选择和隔离失败？
  > 可指定手工组、指定赛事自动匹配或全量扫描；指定失败对外报错，全量/定时逐赛事回滚并继续。
  → 已写入触发条件、异常分支与详细流程第 1、5 步

- [Q2] 候选队与手工组如何校验？
  > 只用当前轮 WAITING，临时排除指定编号，双打须成员齐；手工组完整、编号唯一且均来自候选池。
  → 已写入业务动作 A1-A2 与详细流程第 2-3 步

- [Q3] 比赛初始状态和通知如何确定？
  > 组内报名改 IN_MATCH；恰一名可订场成员则 BOOKING，否则 MATCHED；通知提交后去重尽力发送。
  → 已写入业务动作 A4-A5、详细流程第 4、6 步

- [Q4] 手工分组是否合法仍按当前实现校验：每组人数完整、编号非空且本批不重复，并且报名必须属于当前轮次 WAITING 候选且未被排除？
  > 是。继续按现有候选池严格校验手工组；任一编号不合法、重复、被排除或队伍不完整时，指定赛事事务整体回滚。
  → 已落实到活动契约、异常分支、业务动作 A2 与详细流程第 3 步。

- [Q5] 自动匹配是否继续跳过成员未齐的双打队，并仅以当前轮次 WAITING 报名参与，已晋级到后续轮次的 WAITING 报名不回流？
  > 是。自动匹配仅使用当前轮次 WAITING 报名，成员未齐的双打队跳过；更晚轮次 WAITING 报名不回流本轮。
  → 已落实到业务动作 A1、详细流程第 2 步与边界情况。

- [Q6] 匹配通知是否继续按新 matchId 构造稳定事件、每场参与者去重后提交后尽力发送，失败或未订阅均不回滚匹配？
  > 是。每场以 TOURNAMENT_MATCHED:matchId 为稳定事件，参与者去重后在提交后尽力发送；未订阅或发送失败不回滚匹配。
  → 已落实到 @notification.delivery、业务动作 A5 与详细流程第 7 步。
